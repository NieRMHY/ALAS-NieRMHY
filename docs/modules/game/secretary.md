# 秘书舰轮换

> 根据好感度识别、候补状态和选船策略轮换秘书舰，并安排下一次检查。

## 1. 模块概述

秘书舰任务把截图识别结果转成轮换决策。主秘书舰未达到实现中的好感度上限时，只安排下次检查；达到上限后，优先按照候补与筛选配置更换，并重新识别主槽验证结果。

## 2. 模块职责

### 负责

- 进入秘书舰分组，识别主槽及其他槽位的等级、好感度。
- 临时关闭随机分组，选择候补或从船坞选船，处理确认与恢复。
- 根据最终识别结果安排调度时间，发送轮换通知。

### 不负责

- 全船坞扫描、账号舰船数据库和全局最优选船。
- 调度器的重启恢复；这些行为由任务上层处理。

## 3. 模块位置

源码位于 `module/secretary/`。

| 文件 | 职责 |
| --- | --- |
| `secretary.py` | `Secretary` 任务、轮换决策、调度与通知 |
| `scanner.py` / `group_scanner.py` | 主秘书舰与分组槽位识别 |
| `ship_scanner.py` / `ocr.py` | 船坞候选识别、好感度 OCR |
| `dock.py` / `slot.py` | 船坞操作与槽位定位 |
| `assets.py` | 按钮及识别区域定义 |

## 4. 核心入口

`alas.py` 的 `secretary()` 惰性导入 `Secretary`，传入当前配置与设备，调用 `run()`。排查轮换问题从 `run()` 开始，排查选船问题进入 `search_ship()`，排查长周期调度进入 `schedule_next_run()`。

## 5. 核心组件

`Secretary` 组合 `SecretaryDockMixin` 与 `UI`。主槽扫描器输出姓名、等级和好感度；分组扫描器按五个槽位构造识别结果；船坞扫描器处理候选舰船与已选择状态。

`FAVORABILITY_LIMIT = 90` 同时参与是否轮换、候选排除和下次检查时间计算，修改时需要一起检查这些调用点。

## 6. 工作流程

1. 获取截图，必要时从主界面进入个人信息和秘书舰分组。
2. 记录随机分组是否开启，在本轮操作期间关闭它。
3. 识别主秘书舰；未达到上限就安排下次检查并返回。
4. 达到上限后扫描分组并发送轮换前通知。所有槽位均达到上限时进入批量替换；否则按 `BackupEnable` 选择候补流程或直接更换主槽。
5. 候补流程筛出非主槽、等级有效、好感度未满的舰船，按高低好感度策略排序并拖到主槽。没有候补时尝试补入第 5 槽，再次扫描和提升。
6. 更换后重新识别主槽。操作返回成功但主槽仍满好感度，也按失败延后，避免立即再次运行。
7. `finally` 尝试退出船坞，并在原先开启随机分组时重新开启它。正常走到函数末尾才执行回主界面；提前返回也会执行 `finally`。

批量替换中至少成功一个槽位便可能返回成功，因此不能把这个返回值解释为所有槽位都已换完。最终主槽识别是另一道检查。

## 7. 调用关系

上游是调度器；下游是 `UI`、船坞筛选与排序、设备拖动、OCR、配置调度及通知服务。通知实现和截图识别不共享相同的执行时序。

## 10. 配置

以下选项位于 `Secretary.Secretary.*`，代码以 `self.config.Secretary_*` 访问。

| 参数 | 默认值 | 行为 |
| --- | --- | --- |
| `CustomFilter` | `ultra > super_rare > elite > rare > common` | 按稀有度顺序查找候选 |
| `LowFavorabilityPriority` | `false` | 是否优先低好感度 |
| `FavouriteOnly` | `true` | 船坞查找仅使用收藏舰船 |
| `BackupEnable` | `true` | 使用候补提升流程 |
| `CheckInterval` | `0` | 大于零时按指定小时数检查，否则自动计算 |
| `Notify` | `true` | 控制专用外部通知 |
| `OnePushConfig` | `provider: null` | 专用推送配置；未配置有效 provider 时回退错误推送配置 |

自动检查时间按实现中的「距 90 好感度的差值 × 6 小时」计算。这是调度估算，并非持续测量的增长速度。该任务允许较长的 `NextRun`，不能套用普通任务的短周期上限。

## 11. 异常与错误处理

未选到候选、替换未成功或最终识别未通过时，走失败延后。`finally` 中恢复页面或随机分组失败会记警告，避免覆盖原来的异常。

扫描结果不能仅靠 `None` 判断可靠性：扫描器通常会构造结果对象，部分识别失败会落为数值零。修改容错时应区分“确实为零”和“OCR 失败”。

## 12. 并发与线程模型

游戏交互在任务线程中执行。通知由 daemon 线程发送，线程内还会读取当前配置，并调用 WebUI 通知。任务不会等待所有通知线程完成，进程退出前不保证发送完毕；也不能把这些读取描述成不可变的配置快照。

## 16. 修改注意事项

- 船坞搜索只扫描当前第一页，降序查找没有候选时可转升序重试；不要将其描述为遍历全部船坞。
- 候选会排除已选择、好感度达到上限，以及等级低于 20 且好感度为零的舰船。
- `restore_dock_state()` 恢复的是约定的筛选、排序与收藏状态，不是完整还原进入前的快照。
- 候补拖动后现有实现有固定等待；若改成状态检测，需要同时验证拖动后的槽位和截图更新，不能只删等待。
- 分组满好感判断针对扫描结果执行 `all()`。未解锁槽位和识别误差可能影响结果，不能假设扫描结果一定等于全部有效舰船。

## 19. 调试方法

先区分失败阶段：主槽 OCR、候补扫描、船坞筛选、拖动确认或最终复查。识别问题用对应服务器的已有截图重放，调度问题检查 `CheckInterval` 与保存后的 `Scheduler.NextRun`。

增加回归测试时，可分别模拟候选列表、配置调度和通知发送；不要为测试候选排序直接构造连接真实模拟器的任务实例。当前没有独立的 `test_secretary` 测试模块，不能将其他配置测试视为整条轮换流程的验收。
